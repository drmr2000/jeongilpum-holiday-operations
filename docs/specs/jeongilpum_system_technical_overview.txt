보관 문서 안내

이 문서는 과거 기술 개요 기록입니다. Supabase, Postgres, `fulfillments`, `sales_seasons`, 고객 장부는 현재 구현을 설명하지 않습니다. 현재 구조는 상위 `docs/`의 as-built 문서와 source code를 기준으로 판단합니다.

2. 화면별 역할

- /, /kiosk: 상품·맞춤주문, 방문/택배, 주소·일정 선택, 최종 주문접수
- /kiosk/custom: 20만원 이상 맞춤주문 구성
- /sales: 날짜별 주문표, 검색, 상세, 고객도착, 상태·결제·외상 관리
- /admin: 기존 판매장 호환 화면과 일정 미지정 legacy 주문 관리
- /workshop: 작업수락→작업시작→준비완료, 긴급도·생산량·고객도착 관리
- /workshop/production: BOM 기반 생산량, Batch, 이력번호, Skin Pack 생성
- /workshop/packages/:code: 패키지 구성·QR·라벨·이력 확인
- /settings: 상품, 판매기간, 제품사진 URL, 키오스크 안내문구 설정

화면 이동은 공통 우측 navigation banner가 담당한다.

3. 주문 처리 원리

키오스크 입력
→ sessionStorage 임시 초안 보존
→ POST /api/orders
→ 서버 입력 검증 및 D1 상품가격 재조회
→ D1 batch 실행
   ├─ orders
   ├─ order_items
   ├─ fulfillments
   ├─ fulfillment_items
   ├─ 한정상품 reservation
   ├─ 맞춤주문 customization
   └─ order_events
→ 전체 DB 반영 성공 후에만 주문완료 표시

핵심 원리:
- 상품 가격은 브라우저 입력을 신뢰하지 않고 서버가 D1에서 다시 조회한다.
- 주문 당시 상품명·가격·고객정보를 snapshot으로 보존한다.
- idempotency_key와 unique index로 중복주문을 방지한다.
- 여러 INSERT는 D1 batch로 묶어 원자적으로 처리한다.
- 방문수령은 pickup_at, 택배는 ship_date를 일정 기준으로 사용한다.
- 맞춤주문 상세는 order_item_customizations에 저장한다.
- fulfillment 없는 기존 주문은 삭제·추정하지 않고 일정 미지정으로 유지한다.

4. 판매장·작업장 동기화

현재는 Supabase Realtime이나 WebSocket이 아니라 polling 방식이다.

- 판매장과 작업장이 2.5초마다 D1 API 재조회
- 브라우저 focus 복귀 시 즉시 재조회
- 네트워크 online 복구 시 즉시 재조회
- fetch cache: no-store
- API Cache-Control: no-store, no-cache
- 활성 화면 기준 신규 주문이 약 2.5~3초 안에 반영

D1이 Single Source of Truth이며 화면 state나 브라우저 저장소는 운영 데이터 원본이 아니다.

6. 생산·재고 원리

날짜별 주문수량 × 상품별 BOM = 부위별 총 필요팩
부위별 총 필요팩 - 미배정 available Skin Pack = 추가 생산 필요량

생산 과정:
1) 상품별 BOM으로 부위와 팩 수 계산
2) 현재 가용 Skin Pack 차감
3) 추가 필요량을 production target으로 제시
4) 이력번호 등록 후 Production Batch 시작
5) 중량 저장 1회마다 Skin Pack과 라벨 1개 생성
6) 필요한 부위가 준비되면 패키지 조립
7) 패키지 QR과 assignment history 생성
8) 조기도착 시 가용팩으로 우선 조립
9) 불가능하면 조건이 맞는 완성 패키지를 1:1 재배정

QR에는 고객명·전화번호·주소를 넣지 않고 내부 패키지 식별정보만 사용한다.

7. 인증과 권한

- Sites 전체 접근 모드는 public
- /kiosk는 비로그인 고객 주문 가능
- /sales, /admin, /workshop, /settings는 공용 운영 암호 필요
- HttpOnly 운영 세션을 사용
- 운영 API는 공용 운영 세션을 추가 확인
- 관리자 권한은 서버에서 판단
- 비로그인 요청은 401, 비운영자는 403

8. 안전성과 감사 원리

- 주문·결제·Skin Pack에 idempotency 적용
- 상태 변경 시 예상 version을 비교하는 낙관적 잠금 적용
- order_events에 주문상태·도착·결제·외상·패키지 이력 저장
- configuration_events에 상품·설정 변경 저장
- 취소는 DELETE 대신 cancelled 상태와 감사이력으로 보존
- 한정상품 주문 취소 시 reservation 해제
- 구조화 로그에는 ID·일정만 기록하고 이름·전화·주소는 제외
- 결제 기능은 PG 연동이 아니라 운영자가 실제 결제 결과를 내부 장부에 기록하는 구조

10. GPT와의 관계

- Codex/GPT는 코드 작성·진단·테스트·배포 작업에 사용됐다.
- 실제 고객 주문 과정에서는 GPT API를 호출하지 않는다.
- 프롬프트·토큰 비용·모델 응답 저장·OpenAI API key가 없다.
- ChatGPT와 연결된 실행 기능은 없다.
- GPT 장애나 사용량 제한이 주문·판매장·작업장 운영에 직접 영향을 주지 않는다.

12. 참고사항

- .env.example에 Supabase 변수 3개가 남아 있으나 실제 코드에서는 사용하지 않는다.
- 제품사진은 URL 저장 방식이며 자체 파일 업로드 저장소는 없다.
- 결제·외상은 내부 운영기록이며 실제 금융기관 정산 시스템이 아니다.
- 생산·재고 기능을 Production에 적용하려면 Production 백업 후 0005 migration을 먼저 적용하고 앱을 배포해야 한다.
